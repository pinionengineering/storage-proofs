BJO, SW-Private, and SW-Public timings are the same in every row — none use RSA. PDP costs grow roughly as O(k²) in the key bit-length k. SW-Public Verify performs two BN256 pairings and dominates verification cost across all key sizes.

Prove / Respond Latency vs Challenge Size

All four schemes inspect more blocks as C/V/L grows, so all scale linearly. The gap between curves is the per-block primitive cost: RSA modexp (PDP) > BN256 G₁ scalar mult (SW-Public) > HMAC (BJO) ≈ Z_P multiply (SW-Private).

Verify Latency vs Challenge Size

PDP Verify is one RSA exponentiation — constant in C regardless of how many blocks were challenged. BJO Verify re-derives V block indices and checks the inner-code response — linear in V. SW-Private Verify recomputes L HMAC block hashes plus S Z_P multiplications — linear in L. SW-Public Verify evaluates two BN256 pairings — constant in L but much slower than all others. Comparing with the prove chart above reveals whether prove or verify is the bottleneck at each challenge size.

Setup Cost vs File Size

PDP setup costs one RSA exponentiation per block. BJO setup includes Reed-Solomon encoding (O(n²/k) GF(256) ops) plus Q sentinel computations. SW-Private setup is one HMAC + S Z_P multiplications per block. SW-Public setup is S G₁ scalar multiplications per block.

Tag Generation Time vs Block Size

PDP is nearly flat — the block enters only via a short HMAC, so the RSA exponentiation cost dominates. BJO processes every byte through Reed-Solomon encoding, giving linear scaling. SW-Private splits each block into S sectors (HMAC + Z_P per sector) — linear at a lower slope than BJO. SW-Public does S G₁ scalar multiplications per block; the fixed curve-operation cost dominates, making it expensive at all block sizes but with modest growth.

Server Storage Overhead vs File Size

Extra bytes the server stores beyond the raw data blocks. PDP stores one RSA-modulus-sized tag per block — dominant at production key sizes. BJO stores parity blocks (linear in n at the RS rate) plus a small fixed sentinel array. SW-Private stores only a 16-byte Z_P element per block — the smallest overhead. SW-Public stores a 64-byte G₁ point per block. Neither SW scheme requires parity or sentinels.

Challenge Wire Size vs Challenge Count

PDP and BJO challenges are constant-size regardless of C or V — block indices and coefficients are derived server-side via PRF/PRP without being transmitted. SW-Private and SW-Public transmit explicit index + coefficient lists: 1 + L×20 B and 1 + L×36 B respectively (SW-Public is wider because BN256 Z_q is 256 bits).

Proof Wire Size vs Challenge Count

All four schemes produce constant-size proofs regardless of challenge size. The server aggregates all L/C/V block contributions into a fixed-size summary before responding. BJO is the smallest — one field element plus a precomputed AES-GCM sentinel. SW-Public is the largest — one 64-byte G₁ point sigma plus S×32-byte Z_q mu values. This aggregation property is a key advantage over naive sampling schemes.

Detection Efficiency — P(detect) per Microsecond of Server Prove Time

Normalises detection probability by server compute cost: how much security do you purchase per µs of server CPU time? Higher is better. A scheme that looks slow in raw latency charts may still be efficient if it audits many blocks cheaply. BJO's P(detect) is divided by the larger n_total (including parity blocks), which reduces its apparent efficiency. This chart answers the practical question: "given a fixed server compute budget, which scheme maximises the probability of catching a cheating server per audit round?"

Cumulative Compute Cost over k Challenges (BJO Re-upload Staircase)

Total microseconds of compute to run k challenge rounds over the same file. PDP, SW-Private, SW-Public: pay setup once, then k × prove_time (straight lines). BJO: re-encodes the file every Q challenges (staircase), paying full encode cost again. Once k exceeds Q, BJO's staircase overtakes the unlimited schemes for workloads with heavy auditing. The crossover point shows at which k BJO's re-upload overhead starts dominating.
